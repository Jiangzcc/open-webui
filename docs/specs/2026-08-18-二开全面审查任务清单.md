# 一、产品功能需求（优先级最高，优先实现）

> 仅描述目标行为，**不规定实现过程**。执行 AI 按最佳实践自行设计数据模型、接口、组件结构。须符合 AGENTS.md：独立扩展模块 + `ext_` 命名空间 + 独立迁移链、UI 响应式+触屏+a11y+i18n(补 zh-CN)、不动上游表/迁移、金额 Decimal。标 ❓ 处 AI 自行取合理默认，不阻塞。

## F1. 卡密充值积分

**目标效果**：用户可通过输入卡密（兑换码）自助充值积分，无需管理员手动调账。

**用户侧**：
- 用户在积分入口处有「卡密充值」入口，可输入卡密码兑换
- 兑换成功后积分余额即时增加，并可在流水里看到这笔记录
- 卡密码错误/已用/已作废时给出明确反馈
- 同一卡密只能兑换一次，兑换后不可重复使用
- 兑换操作有频率限制，防刷接口

**管理侧（admin）**：
- 管理员可生成一批卡密（指定面值即积分数、数量、可选过期时间、可选单用户限兑次数）
- 卡密生成后明文只返回一次，可批量导出（如 CSV），之后不可找回明文
- 可查看卡密批次、兑换率、已用/未用/作废状态
- 可作废未用卡密
- 生成/作废操作有审计记录

**产品要求**：
- 卡密不可被枚举/猜测（随机性强），存储不可逆（防拖库泄露）
- 兑换与余额增加须原子化，防止并发兑换同一码导致重复到账
- 复用现有积分账户/流水/对账体系，这笔收入能在对账里体现
- ❓ 积分是否真付费化：AI 自行判断措辞与语义（内部积分体系下可用「兑换」，但保留卡密面值=积分数的产品语义），不阻塞

## F2. 提示词标签库

**目标效果**：用户在生图/生视频输入提示词时，可从预设的专业标签库里一键选择标签插入到提示词，提升提示词质量与出图效果。

**用户侧**：
- 提示词输入框旁/下方有标签面板，展示可用标签
- 标签按分类折叠（如 光影/构图/风格/镜头/画质/人物/场景），点分类展开
- 点击标签即将其对应文本插入提示词（光标处或末尾，按模型习惯分隔，如英文逗号）
- 已选标签可取消（从提示词移除对应文本）
- 支持搜索过滤标签、常用标签置顶/最近使用
- 标签可按当前选中模型过滤显示（某标签只对特定模型有意义时不显示）
- 含负面词的标签应进入 negative_prompt 而非主提示词
- 移动端窄屏下标签面板不挤压提示词区（如可滑出抽屉），触控友好

**管理侧（admin）**：
- 标签与分类的增删改查、排序、启用/禁用
- 每个标签含：中文展示名（供用户识别）、实际插入文本（通常英文，供模型识别）、分类、可选适用模型、是否负面词
- 批量导入导出标签
- 内置一套开箱即用的专业标签库（中英双语：中文 label + 英文 insert）

**产品要求**：
- 标签插入在前端完成，纯提示词字符串组装，不侵入生成/计费链路
- 标签库管理走后端，生成时只读，性能开销小
- 标签文本 i18n（中文 label + 英文 insert，模型吃英文）
- ❓ 初版标签库内容：AI 自行设计一套开箱即用的专业标签库初版（按 光影/构图/风格/镜头/画质/人物/场景 等分类，每类若干中英双语标签，基于生图/生视频通用最佳实践），不阻塞
- ❓ 是否分模型挂标签：初版做通用库即可，AI 自行决定是否预留按模型过滤的扩展能力

## A 架构归属层（降升级成本，最高优先）

### A1 ⭐ fal.py 系列迁出上游目录
- **归属**：`utils/images/fal.py`(763行)/`fal_models.py`(486行)/`test_fal*.py`
- **动机**：上游 0.10.2 的 `utils/images/` 只有 `comfyui.py`，二开把 fal 文件放进该目录，上游加同名即冲突，升级时被 merge 工具误处理。升级成本最高点。
- **做法**：迁到 `extensions/images/` 或 `extensions/fal_runtime/`；`routers/images.py` 只留薄调用点。
- **影响**：纯搬迁+改 import，无行为变更。

### A2 四份 migrations/runner.py 抽共享基类
- **归属**：creations/credits/model_ops/provider_ops 各一份 runner.py
- **动机**：四份模式相似但细节不一致——model_ops/provider_ops 缺上游 head 校验、用阻塞 `pg_advisory_lock`，creations/credits 有 `_validate_upstream_head`+try_advisory_lock+超时。
- **做法**：抽 `extensions/common/migration_runner.py` 的 `ExtensionMigrationRunner` 基类，四模块传版本表名/锁命名空间。
- **关联**：#31

### A3 两份 limits.py 抽共享并发计数器
- **归属**：`videos/limits.py` + `images/limits.py`
- **动机**：各维护 `_active_by_user`+`asyncio.Lock`，代码几乎相同，多 worker 迁 Redis 要改两处。
- **做法**：抽 `extensions/common/concurrency.py` 的 `UserSlotLimiter`。
- **关联**：#41

## C 缓存与性能

### C1 catalog 统一缓存
- **归属**：`fal_catalog/loader.py` + `utils/images/fal_models.py`
- **动机**：图片侧 `_CATALOG` 模块级单例，视频侧 `load_video_catalog` 无缓存每次重载 89 模型(#4 #8)。
- **做法**：`loader.py` 加 `@lru_cache(maxsize=1)`（FalCatalog frozen+MappingProxyType 不可变，缓存安全）。

### C2 RateLimiter 异步化

- **动机**：RateLimiter 全同步，async 端点里同步 INCR/EXPIRE 阻塞事件循环(#7)。
- **做法**：rate_limit.py 加异步 Redis+`is_limited` async，或 `anyio.to_thread.run_sync` 包装。⚠️ 侵入上游需评估冲突。
- **关联**：#7

### C3 定价数据链路重做

## D 前端抽象

### D1 ⭐ API 层抽共享 request helper
- **归属**：6 个 `apis/{credits,videos,creations,provider-ops,media-model-ops}/`

- **做法**：抽 `apis/common/request.ts` 统一结构化错误(含 detail 嵌套)+AbortSignal+默认超时+网络故障包装。
- **关联**：#13

- **做法**：内置 `min-h-9`+`focus-visible:outline-2`+`aria-pressed`/`role=switch` 的共享组件。

### D3 统一两套游标实现
- **归属**：`creations/discovery_service.py:249` vs `schemas.py:419`
- **动机**：两套游标解码，discovery 宽松（无 canonical/版本/类型守卫），schemas 严格。易在演进中语义漂移。
- **做法**：⚠️ 两者 payload 结构不同——discovery 为三字段 `{p,t,id}`（返回 `int,int,str`），schemas 为两字段 `{v,created_at,id}`（返回 `int,str`），**非简单替换**。正确做法：discovery 采用 schemas 的严格校验模式（canonical 规范化 + 版本字段 + 类型守卫），或抽出支持多字段的通用 keyset 解码器，再让 discovery 复用。
- **关联**：~~#46~~（原 bool 可绕过已确认为非安全问题并删除，此项降为纯代码质量重构）

### D4 playground demo dev 门控

- **动机**：进生产 bundle（有 admin 守卫但代码打进包）。
- **做法**：`import.meta.env.DEV` 门控或移到不参与生产构建目录。

### E1 provider_ops 多厂商路由化
- **归属**：`provider_ops/platform_sync.py`
- **动机**：`sync_fal_platform` 写死 `_PROVIDER='fal'`，models/schemas 是 provider-neutral 但 sync 只支持 fal。
- **做法**：重构 `sync_platform(provider,...)` 按 provider 路由 client，未来接 replicate/runway 只加适配器。当前先 docstring 标"仅 fal"。

### E2 video 恢复机制统一
- **归属**：`videos/service.py`+`registration.py`
- **动机**：三套恢复（recover_video_task/recover_incomplete_tasks/_video_recovery_worker）各维护 CancelledError/Exception/终态处理。
- **做法**：统一 `VideoRecoveryOrchestrator`。配合 B1 收益最大。
- **关联**：#1 #20

### E3 sync 后台任务化
- **归属**：`provider_ops/router.py:100`
- **动机**：手动端点阻塞 HTTP，反代超时触发 CancelledError(#9)。周期 worker 已后台。
- **做法**：改"提交任务返回 run_id+后台执行+轮询状态"。
- **关联**：#9 #24

### 重构优先级
做 3 件先：**A1**(fal 迁出降升级成本) + **B1**(service.py 拆分根治恢复不一致) + **D1**(request helper 解 #13)。
排序原则：架构归属层→模块拆分→缓存/前端→可扩展性。重构多为多条问题的根因解，修问题时可顺带做。
